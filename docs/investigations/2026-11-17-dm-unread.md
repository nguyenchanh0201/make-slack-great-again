# Already-read DMs showing unread: investigation

Investigated MSGA commit `8a5c2ef` on 2026-11-17. No production code changed.
Two targeted checks reproduce incorrect read-state handling on this revision.
These establish defects, not proof of the exact live incident reported by the user.

## Finding 1: explicit zero is replaced by a guessed unread message

`mapjson::toConversation` (`src/app/slack/slack_json.cpp:423`) reads
`unread_count`, then uses a timestamp comparison whenever the count is not
positive. It does not distinguish an explicit zero from an absent field.

Given this response fragment:

```json
{
  "id": "D1", "is_im": true, "user": "UMIRA",
  "last_read": "1800000000.000200",
  "latest": {"ts": "1800000000.000300"},
  "unread_count": 0, "unread_count_display": 0, "mention_count": 0
}
```

The mapper produces `unread=1`. A later timestamp alone does not prove an
unread incoming message: for example, the newer message can be the user's own.
This inferred count can feed DM enrichment, reconnect patches, and authoritative
read reconciliation. Each consumer has additional merge rules, so the mapper
test alone does not establish that every such response restores a visible badge.

## Finding 2: remote read event cannot clear a stale badge with newer own message

`applyAuthoritativeReadObservation` (`src/app/slack/slack_backend.cpp:3842`)
starts with the current unread/mention counts. When `latest > lastRead`, it
replaces them only if the incoming unread count is positive. An explicit zero
therefore leaves the previous counts intact.

The fake-server test uses the actual WebSocket event path:

1. Cache an incoming DM at timestamp 200 and the user's own reply at 300.
2. Start with one unread incoming message and a read cursor just before 200.
3. Deliver `im_marked` with cursor 200 and both display counts equal to zero.
4. MSGA advances its cursor to 200, but retains unread=1 and mentions=1.

There is no genuinely newer unread incoming message in this reproduction.
The sidebar consumes these retained counts, so it continues to show unread.
This reproduces failure to clear a badge after a remote read, rather than a
captured clear-then-reappear transition or a desktop banner.

## Endpoint and field semantics

Provenance: documented Slack Web API and RTM event contracts (`conversations.info`, `conversations.list`, `*_marked`, `client.counts`). No live Slack payloads were captured in this investigation.

| Endpoint / source | Fields retained | Domain and badge semantics |
|---|---|---|
| `conversations.info` / roster entries (`conversations.list`, `users.conversations`, `im.list`, `client.userBoot`) | `unread_count`, `mention_count` in `raw`; `unread_count_display`, `mention_count_display` in `display` | `unread_count` is the raw total (may include filtered, system, or own activity). `unread_count_display` is the filtered count matching the visible badge when present (DMs/MPIMs). Channels often omit display counts or report `unread_count: 0`. Unavailable `display` fields must not silently fall back to `raw`. |
| `*_marked` (`im_marked`, `mpim_marked`, `channel_marked`, `group_marked`) | `unread_count_display`, `mention_count_display` in `display`, scoped to `ts` | Display-domain counts at cursor `ts`; either count field may be omitted. A fresh `conversations.info` response confirms the same metric only when it carries `unread_count_display` / `mention_count_display`; raw `unread_count` cannot confirm or refute a display count. |
| `client.counts` IM / MPIM / channel entries | `dm_count` (in `raw`, IMs), `mention_count` (exact), `has_unreads` (optional bool) | `mention_count` is exact. `dm_count` is retained as source-specific raw data rather than assumed equivalent to `unread_count_display` for all kinds. `has_unreads == true` is an inexact lower bound (`>= 1`), not an exact message count; `has_unreads == false` indicates no unreads in that entry. |

## Next step

Correct the zero-versus-missing distinction and reconcile an authoritative zero
against actual newer incoming-message evidence, preserving the existing guards
for genuinely newer arrivals and intentional Mark unread. Do not simply clear
every count on every zero response: delayed responses can predate new messages.

For the user's exact occurrence, still establish whether it is a sidebar badge
returning, a repeated desktop banner, or a read conversation merely reappearing
in the list, and whether the read occurred in MSGA or official Slack. A live
trace should record read cursors, counts, event/request ordering, and decisions;
message bodies and credentials are unnecessary. No official Slack internals or
live Slack payloads were inspected during this investigation.
